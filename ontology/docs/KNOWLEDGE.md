# Knowledge discovery

The model publishes domain knowledge facts: stable identities, descriptions,
relationships, logical types, values and declared business constraints. Tool
usage, request syntax, retrieval recipes and Agent workflows belong to consumers.
The host collects the complete graph and can expose compact projections to Agents.

The engineering boundary is versioned: discovery declares
`knowledge_contract: "ontology-knowledge-v3"` and
`intent_contract: "ontology-intent-v1"`. Consumers must reject incompatible
snapshots explicitly. Updating Intent grammar requires reviewing the consumer's
versioned tool help together with parser tests; changing knowledge descriptions
must preserve business semantics without adding tool instructions.

## Info protocol

`knowledge::knowledge_service_factory(payload, domain)` binds a prepared Model
and returns a pure `Fn(Value) -> Value` request handler.
`knowledge::serve_value` is the equivalent unbound entry.
No database connection or SQL backend is required.

Mount `knowledge::knowledge_info_method_factory(payload)` in a
`<domain>/info` service slot. Telora routes by method and passes only input
to the slot; do not pass an envelope inside transform.

```json
{"method":"foo/info","input":{"key":"index"}}
{"method":"foo/info","input":{"key":"Dataset/example"}}
```

Requests have exactly method and input; info input is exactly `{key:<string>}`.
The response is `{"Document":{"Found":{...}}}` or
`{"Document":"NotFound"}`. Every Found node has
`{key,address,type,description,links,detail}`.
description contains label, aliases, localized text, summary and explicit terms.
links contains `{type,key,role}` entries: Member structural membership,
Traversable declared relation endpoints, and Related explanatory associations.
Related never authorizes a query traversal.

Unknown and invisible keys return NotFound.
`info("terminology")` returns NotFound: vocabulary is generated by consumers
from discovery roots and structured info documents.
Malformed input and unsupported fields fail with a structured diagnostic
including the JSON path and concrete validation reason.
Identity authentication and access control belong to the host.

## Top-level Index

`info("index")` returns an Index with detail
`{revision,key_patterns,encoding}`.
key_patterns lists `{kind,pattern}` for concrete knowledge nodes. encoding
describes stable URI component identity. Member links include primitive types,
so index plus discovery roots reaches the complete published graph.
The index enumerates no business instances.

Key prefixes equal their kinds, including `Ty/{ty}`.

| Node kind | Key pattern |
| --- | --- |
| Dataset | `Dataset/{dataset}` |
| Field | `Field/{dataset}/{field}` |
| Dimension | `Dimension/{dataset}/{dimension}` |
| Measure | `Measure/{dataset}/{measure}` |
| Relation | `Relation/{relation}` |
| Ty | `Ty/{ty}` |
| Value | `Value/{ty}/{value}` |
| TimeRole | `TimeRole/{dataset}/{field}` |
| BusinessLink | `BusinessLink/{hub}/{link}` |

Encode each canonical name as one URI component exactly once.
Returned keys are complete: pass them unchanged to info.
Names, aliases and labels are distinct from canonical Intent IDs.

## Concrete Knowledge

Dataset detail contains `{id,grain,time_roles,references,field_roles}`.
Its Member links directly identify published Fields, Dimensions, Measures,
Relations, TimeRoles and BusinessLinks.
Dimension links identify its Field, logical Types and declared Values.
A relation publishes its endpoints, cardinality and shape from the same
Prepared Model used for query lowering.

Field detail contains `{id,dataset,nullable,logical_type,roles,reference_ids}`.
Value detail contains `{id,ty,wires}`. Ty detail has id; its description
and structured operations explain the logical value domain.
Dimension, Measure and Relation preserve the corresponding Model brief.
Measure detail includes `sampling`, when declared: source field, unit, aggregate
and role (`Primary` or `SampleSummary`). Sampling metadata belongs to that
Measure and has no separate knowledge key. `sample_measure` directly declares a
primary sample measure and its unit; `sample_aggregate` declares another statistic on the same field
with the same unit. Dataset kind `Metric` describes a sampling population, and
Field role `Metric` describes quantitative use; neither is a knowledge node kind.
Metric and TimeRole identify their owning dataset. BusinessLink contains
`{id,hub,direction,guard}`. Latest Measure detail includes structured selection
facts: clock keys, complete dataset grain keys, descending time, ascending
grain ties with NULL first, excluded NULL time, and preserved NULL values.
Dimension detail includes utc_bucket when declared, with calendar unit; field
and input type identify the source and output time domain.

Field visibility comes from grain, time roles, visible dimensions, measures
and sampling measures. A private physical column alone is not published.
A Field ID is not automatically a queryable Dimension ID.
Logical type operations do not grant field authorization: inspect the
Dimension's ops, filterable flag and time role.

Dimension input_kinds and input_docs describe accepted logical values.
Input documentation comes from @doc on FilterInputKind variants.
Time roles declare semantics, encoding and authoritativeness; relative calendar
boundaries and local timezone ambiguities must be resolved externally.
Time roles and UTC bucket metadata preserve time meaning independently of the
consumer query syntax.

`business_link_description(id,label,summary)` describes a declared link on its
hub. `term` supplies searchable aliases and their explanations. BusinessLink
names describe traversal through two endpoint relations; direction and guard
remain explicit query contracts, and names do not establish device hierarchy.

Dataset references are alternative complete unique addresses `{id,fields}`.
Any NULL member makes a reference unavailable; this does not create a total key
or query grain. Field nullable derives from Option(T).
Field roles are Appellation, Reference, Classification and Metric; roles do not
grant query access. Hidden fields and incomplete visible references are excluded.
See [FIELD-ROLES.md](FIELD-ROLES.md).

@knowledge_doc changes explanations without granting visibility or query
capabilities. @related_to adds explanatory references without creating query
relationships. knowledge_lookup_factory prepares one catalog for repeated
typed lookups; service factories likewise initialize their catalog once.
The catalog caches visible Dataset briefs and indexes documentation, related
references and explicit terms by key. Member lookups construct only the requested
node; full member documents are not cached.

Preparation checks dimension ID uniqueness through a bulk dictionary; duplicate
diagnostics select the first conflicting declaration in source order. Dataset
publication prepares entity-local field membership, and catalog construction
consumes resolved dimension entries. Input-type documentation metadata is prepared
once and shared across dimension descriptions. Profile validation checks operator
and scalar capabilities together while traversing expressions.

Measure model preparation with a release compiler, serially against the same
source revision and resource limits. For example, from the repository root:

```sh
printf '{"method":"ic/discovery","input":{}}\n' | /usr/bin/time -v /path/to/telora/target/release/telora \
  -C icloud_model --initialization-fuel 1000000 --request-fuel 10000 \
  --with-memory-limit 2048 run icloud_model
```

This includes compilation, model preparation and service initialization. Record
elapsed and user CPU time separately. Snapshot startup benchmarks below measure
loading an already prepared model.

`node scripts/benchmark-knowledge.mjs --artifact <snapshot> --full --output <report.json>`
measures snapshot startup through the first discovery response, warmed single-key
requests and complete traversal. The report includes compact JSON byte sizes and
SHA-256 hashes for comparing every node across snapshots. On Linux it also records
runner resident memory; this includes the runtime and transient allocations, not
just the catalog. Startup excludes source compilation and snapshot initialization.

## Programmatic Discovery

`knowledge::knowledge_discovery_method_factory(payload)` mounts
`<domain>/discovery`. It accepts `{}` and returns
`{knowledge_contract,intent_contract,revision,roots,key_patterns,vocabulary}`. `roots` lists complete visible Dataset
and Relation keys. `key_patterns` uses the same definition as the top-level index.
Consumers collect `index` and these roots, then follow direct links.

`vocabulary` declares searchable membership and output shape as
`{kind,group,owner,require}` entries. `group` names the terminology output array.
Optional `owner` is both the detail field and key-pattern placeholder identifying
the owner; Value uses `ty`. Optional `require` names one detail field that must
exist and be non-NULL for inclusion. It is not an expression or conversion.
Kinds absent from vocabulary remain readable but are not vocabulary members.
Consumers distinguish an excluded kind from an unknown kind using `key_patterns`.
An empty vocabulary declares no members; a missing declaration is a contract error.

`description.terms` contains explicit `{term,description}` annotations on each
knowledge point. Together with its label, summary, aliases and localized text,
this preserves the metadata needed for external search vocabulary generation.

## External Indexes

`scripts/derive-discovery.mjs` uses discovery and exact info calls to generate:

- `.terminology.json`: `{revision,datasets,dimensions,measures,rels,types,values,business_links}`.
- `.links.json`: `{revision,links:[{source,target,kind}]}`.
- `.keys.json`: the Dataset/Relation roots.
- `.report.json`: complete manifest coverage and optional baseline comparison.

Business-link terminology entries are `{hub,name,doc,aliases}` and identify
`BusinessLink/{hub}/{name}` using encoded URI components. They are distinct
from Relation terminology; discovery still starts from Dataset/Relation roots.

`--keys roots.json` accepts roots from a standalone file. Unresolved references,
duplicate nodes and owner mismatches fail explicitly. `--compare-prefix`
compares vocabulary names, documents and aliases, and unique reference edges
with local baseline files; differences produce exit status 1.

Dataset, Relation and business Type terms are `{name,doc,aliases}`.
Dimension and Measure terms add `dataset`; Value terms add `ty`.
Only visible nodes are indexed. Physical Fields and primitive Types remain
available through info and do not enter search vocabulary.
A term can match multiple keys; names, aliases and documents support scoped
consumer-side search. An alias without its own declared description uses the
node summary, or the display label when no summary is declared.

Each link matches a reference in its source's info document. Edges are unique
by `(source,target,kind)`; `Member`, `Traversable` and `Related` remain distinct.
For Relation endpoints the source dataset is a Member edge and the destination
is a Traversable edge, retaining both sides of self-relations.
Consumers index edges by target to find referencing knowledge keys.

Value ownership is encoded by `Value/{ty}/{value}`; Dimension ownership by
`Dimension/{dataset}/{dimension}`. Reverse type references find dimensions
using a type. Read their local constraints to determine accepted values.

## Mechanical Exports

```sh
node scripts/build-knowledge-snapshot.mjs --module icloud_model --domain ic \
  --output bin/icloud_model.snapshot.wasm --with-memory-limit 2048
node scripts/derive-discovery.mjs --output-prefix bin/icloud_model
node scripts/export-knowledge-markdown.mjs
node ontology/tools/knowledge-export.mjs http://127.0.0.1:8080/foo/info > /tmp/foo-knowledge.json
node ontology/tools/knowledge-html.mjs /tmp/foo-knowledge.json > /tmp/foo-knowledge.html
```

Snapshot publication traverses index, discovery roots and direct references
and records the revision, artifact digest and full visible key set. The HTML
renderer escapes text and rejects duplicate or dangling references.
Access to artifacts is controlled by the host. The model-independent service
engineering protocol is in [USAGE.md](../../USAGE.md).

## Semantic addresses and classified navigation

The engineering knowledge contract is `ontology-knowledge-v3`, with discovery
`addressing: "node-member-uri-v1"`. Each info node includes
`address: {node,member}`. Independent nodes use `datasets/<id>`, `types/<id>` or
`relations/<id>` with member null; owned members use e.g. node
`datasets/<dataset>` and member `fields/<field>`. IDs in addresses are separately
URI component encoded once. Each link declares a role identifying its target
category: fields, dimensions, measures, time_roles, business_links, datasets,
types, values or relations. The model publishes identity and facts; consumers
organize projections and derive classified reverse navigation from these facts.

反向导航由工具层从正向事实派生。模型通过地址表达成员归属，并由父节点列出成员；成员不重复发布归属父节点的链接。关系端点、业务链接端点及度量依赖属于业务事实，仍显式发布。

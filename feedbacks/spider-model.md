# Spider model feedback

本轮测评表明，Resolver 通常能够理解问题，但当前领域契约的部分约束会迫使它拒绝合理
意图或改变返回结果。请基于以下观察重新审视契约、领域词汇、实现与诊断；不要把这些
反馈直接改写成针对测评题目的特例。

## 过强的限制

`INTENT.md` 中“排序目标必须是本请求已选择、出现在 `measures` 或
`dimensions` 中的项”这一规则过强。

例如，用户只要求返回歌曲名称和发行年份，并要求取年龄最小的歌手时，以下意图是合理的：

- 返回项：歌曲名称、发行年份；
- 排序目标：歌手年龄升序；
- 限制：1 行。

歌手年龄不是用户要求的返回项，不应为了满足排序约束而加入返回结果。类似地，按某个
统计值选出最高项时，该统计值也不必必然成为返回列。

## 必要但无法表达的意图

1. 契约只能对 count measure 表达 distinct，不能表达“返回互不重复的维度值”。普通投影
   不是合理替代，因为它会返回重复行。
2. 当前领域词汇有体育场容量，却没有容量的平均值和最大值。能够过滤或返回一个数值属性，
   不代表能够表达用户明确要求的聚合方式。
3. “返回没有任何关联记录的主体”无法表达。返回有关联记录的主体或按关联记录计数，不能
   替代这个意图。
4. “同一主体分别存在满足条件 A 和条件 B 的关联记录”无法表达。把 A、B 同时约束在一条
   关联记录上会改变语义。
5. 当前 `measures` 与 `dimensions` 分栏不能完整表达返回列次序。测评中出现了值集合正确、
   但 measure 被固定输出在 dimension 之前的情况。
6. 跨关系只返回维度时，当前模型会因无法确定查询入口而拒绝，或加入一个未被请求的 count
   来建立路径。后者改变了列数和行粒度，不是合理替代。

## 需要保留的限制

- 未知或未授权的 measure、dimension、filter、关系和排序目标仍应拒绝。
- 值类型不匹配、非法算子、无确定关系路径、不能证明结果粒度的组合仍应拒绝。
- 无法忠实表达时应拒绝，而不是增加返回列、丢弃 distinct、引入不需要的分组，或改变
  重复行语义来换取 `make-query check` 成功。

这些限制的目的都是保证生成结果与请求一致；请检查限制条件是否恰好拦截不安全或不确定
的意图，而不是同时拦截 SQL 中本来合理且确定的形状。

## 诊断不足

不同失败路径目前会汇总成 `invalid spider intent`。该信息不足以区分：未知 ID、不支持的
mode、排序项未选择、类型错误、关系路径不可达，还是该意图类别根本不在契约中。测评中
Resolver 因此反复猜测多个名称和表示形式，单题产生了大量无效 `make-query check` 尝试。

拒绝时的诊断至少应让调用者知道：哪个输入位置失败、违反了哪条契约规则，以及这是输入
可以修正的错误还是模型暂不支持的能力。诊断不得泄露私有 schema 或提供 SQL 拼接入口。

## 验收关注点

请为每项调整增加不复用 held-out 题目的通用测试。成功结果需要同时保持正确的行集合、列
集合、列顺序与重复行语义；仅 SQL 可执行或检查命令返回成功，不足以证明结果忠实。

## Round 3 follow-up

上一轮反馈中的隐藏维度排序、维度 DISTINCT、容量聚合、absence、多个独立 exists 和
dimension/measure 输出次序已经通过执行结果验证。不要回退这些能力。

仍有两个约束问题：

1. “按每组的计数降序取第一组，但只返回分组维度”是合理意图。当前 contract 要求用于排序
   的 count 同时出现在 `measures`，而 `measures` 又必然成为返回列，因此结果多出 count。
   用于分组排序的聚合值不一定是用户要求的返回项。
2. “返回满足两跳关系条件的主体维度”是合理意图。当前 contract 只能通过加入 link-entity
   count measure 建立这条路径，导致结果多出 count，并通过 GROUP BY 折叠原本的行语义。
   关系约束用于限定主体集合，不代表用户请求返回关联计数。

请重新审视 contract 中“参与计算或确定关系路径的项必须同时成为返回项”这一隐含规则。
修正后的成功结果必须只返回用户要求的列；若底层能力仍无法忠实表达，应给出明确的
unsupported 诊断，而不是输出带额外 count 的近似结果。

## Round 4 follow-up

执行结果为 19/21。内部聚合排序已经修复，既有正确结果没有回归。剩余两个问题是同一
意图的同义问法：返回满足 `Singer -> SingerInConcert -> Concert` 两跳存在条件的 singer
维度。

当前领域模型对两个同义问法给出了不一致结果：一个仍使用 link count + GROUP BY 并返回
额外 count，另一个按契约给出明确的 `unsupported`。前者违反了本文件上一轮已经明确的
fidelity rule，不能因为 SQL 可执行且 check 成功就视为完成。

在基础层尚未支持该路径时，所有等价意图都应稳定地给出同一类 unsupported，而不能根据
措辞偶然选择近似。基础层若补足该能力，则应使用忠实的纯维度/存在性表达，返回列、重复
行语义和顺序均以请求为准。请增加同义表达与重复执行的一致性测试。

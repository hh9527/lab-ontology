# Student transcript domain feedback

首轮 held-out 执行评测表明，自然语言意图大多被正确识别，但领域模型的公开词表和角色化
关系覆盖不足。请基于 modeling schema/examples 重新检查模型，不读取 held-out 数据，也不把
评测问题、参考答案或 SQL 写入文档和测试。

## 领域属性覆盖

补齐 schema 中具备清晰业务含义、可安全公开的常用属性，尤其检查：

- Course 与 Section 的描述属性；
- Student、Semester、Address 等主体的业务标识属性；
- Student 的离校日期及其它详情属性；
- 已有名称、描述、标识和日期属性能否用于投影、过滤与隐藏排序。

不要因为属性是主键就一律禁止其作为请求明确要求的业务标识输出。动态值仍必须进入
bindings，物理列名和 Join 路径不得进入 Resolver 公共资料。

## 角色化关系与聚合

Student 到 Address 存在多个业务角色。模型必须显式区分这些角色，并为反向统计选择唯一、
可验证的关系；不得让通用路径搜索在多个外键间猜测。对无法由基础层忠实表达的关联聚合，
继续稳定拒绝，不得退化到另一关系或混合多个角色。

## 返回形状

- 用新增的显式投影顺序保持调用方要求的列序；
- 排序或 HAVING 所需的内部计算不得被当作额外结果列；
- 请求多个属性时不得静默省略未知属性后返回部分结果；
- “详情”必须映射到明确的详情属性，不能用姓名集合近似；
- 关联存在查询应保持主体去重语义。

基础层若已提供同主体属性间比较能力，请在领域契约中以封闭 intent 暴露它，并只允许模型
声明的类型兼容属性对；若基础层尚未发布该能力，则保持明确 unsupported，不做字符串或
SQL 旁路。

补充领域测试覆盖新增词表、角色化关系、列序、未知属性、非法属性对、确定 bindings 和
重复执行一致性。测试使用 modeling 资产中的通用或合成用例，不复制 held-out 问法。

## 关联聚合适配

基础层已经提供封闭的 `lower_internal_related`，可在一条已声明、方向确定的直接关系上，
把关联侧聚合作为隐藏排序项或 HAVING 条件，同时保持外层主体粒度和显式投影。当前领域
Resolver 尚未接通该能力，仍把关联计数建模为普通投影 measure，或把 HAVING 记为不支持；
请修正领域 intent、词表、lowering 和边界文档，不得继续用普通聚合近似。

结合 modeling schema 中已经声明的直接关系，至少检查以下通用形状是否能够被领域契约
封闭表达：

- 以学期为主体，按关联注册记录数隐藏排序；
- 以学位项目或其已选业务分类为主体，按关联注册记录数隐藏排序；
- 以角色化当前地址为主体，按反向关联学生数隐藏排序；
- 以学生为主体，按直接关联注册记录数做 HAVING 阈值比较。

这些形状的最终投影只能包含请求明确选择的主体属性，关联计数不得为了排序或过滤而进入
结果列。HAVING threshold 必须进入 bindings；Top-N 的 limit 沿用现有参数化规则。关系方向、
角色或主体 grain 无法唯一证明时稳定拒绝，不得退回普通 measure、EXISTS、自连接、结果后
处理或手写 SQL。

使用 modeling 或合成数据增加正反向关系、隐藏 Top-N、隐藏 HAVING、投影无 count、阈值
binding、角色歧义拒绝和重复 lowering 一致性测试；同步删除 `INTENT.md` 中与基础层现有能力
相矛盾的“不支持 HAVING”描述。完成后运行计划中的四项检查，并确保已有查询行为不回退。

## 关联聚合回归反馈

基础能力接通后的执行回归确认，隐藏关联排序与 HAVING 已能生成正确的聚合形状，但领域
Resolver 的 internal-related 分支没有应用普通分支已有的显式 projection finalizer。因此，
当调用方提供 `column_order` 时，输出仍退回 dimensions 的声明顺序。请让该分支复用同一套
封闭投影排序逻辑，并增加“隐藏 Top-N + 多主体属性”和“隐藏 HAVING + 多主体属性”的
列序测试；不得为此改变 grouping、ordering、having 或 bindings。

角色化 Current Address 目前只公开标识及 city/state/country，尚未公开 schema 中同一角色的
line 1/line 2。请在保持 current/permanent 路径唯一的前提下补齐这两个角色化属性，使调用方
能在 Current Address 主体粒度明确选择地址标识和文本行，并与隐藏反向学生计数排序组合。
不要借用未定角色的 base Address 属性，也不要合并 current/permanent 关系。增加合成测试
验证三项主体投影、隐藏 count 不出现在结果中、关系方向唯一且显式列序生效。

## 字符串字面量保真

全量回归发现，查询形状与字段映射正确时，调用方仍可能把自然语言中的字符串实体值擅自
改成标题大小写或其它“规范化”形式。SQLite 的等值比较通常区分大小写，这会把正确 intent
变成不同结果。请在领域 intent 文档中明确：除非领域词表声明了可证明的规范化规则，所有
字符串过滤值必须逐字保持请求中的表面形式并原样进入 binding；不得根据常识修正大小写、
拼写、单复数或别名，也不得从 modeling 数据猜测一个替代值。

用与评测值无关的合成字符串增加测试/示例，覆盖小写、混合大小写和缩写值，确认 Resolver
仅参数化而不改写值。未知或疑似拼写问题仍按原值查询，不由领域层静默纠正。

## 数量算子与隐藏排名纪律

回归中仍出现两类已经可表达、但自然语言到 intent 选择不稳定的问题。请在 `INTENT.md` 用
领域无关的判定表明确约束，并用合成示例覆盖：

- “有 N 个 / 数量为 N / 恰好 N 个”映射为 HAVING `eq N`；只有明确出现“至少、不少于、
  N 个以上”等下界语义才映射为 `ge N`，不得把裸数字保守放宽成下界。
- “按关联数量最多/最少，返回主体的若干属性”中，关联 count 只用于 hidden order；除非请求
  明确要求同时显示数量，否则 `measures` 必须为空，count 不得进入 projection。

把这两项写成生成 intent 前的结果形状检查：先枚举请求明确要求返回的列，再单独确定过滤和
排序所需的隐藏计算；禁止因为 checker 接受普通聚合形式，就用额外结果列替代隐藏聚合。
合成测试同时断言 operator、projection、SQL bindings，且不得包含评测实体值或原问题文本。

## 文档契约一致性

最新 `INTENT.md` 已在能力说明和选择纪律中支持 hidden related Top-N/HAVING，但“不支持的
形状”及末尾错误分类仍把“未返回聚合排序/HAVING”标为 unsupported。这是直接矛盾，会使
调用方在同一合法形状上随机选择新能力或拒绝/近似。请删除这两处陈旧描述，并准确改成当前
真正不支持的边界（例如多跳或无法证明唯一直接关系的关联聚合）。全文检索 Top-N、hidden、
HAVING、unsupported，确保每个形状只有一个一致结论；不得只在前文追加例外说明而保留冲突。

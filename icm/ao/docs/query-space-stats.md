# 查询空间统计报告

> 基于 `tmpl-ref.md`（161 条模板骨架）、`query-gen.md`（生成规则）、`query-cases.md`（填槽用例）与 `user_query_cases_ref/`（40 条真实用例）的覆盖度统计。
> 目的：评估 NL→SQL 生成器的覆盖面、识别组合空间的边界与稀疏区。

---

## 1. 模板规模

| 维度 | 值 |
|---|---|
| 原始模板（tmpl-ref.md） | 161 |
| 唯一骨架（去实体类型参数化后） | ~20 |
| 填槽用例（query-cases.md 章节） | 9 章 / 约 200+ 条 |
| 真实参考用例（user_query_cases_ref） | 40（Q0001–Q0040） |

**核心结论**：161 个模板不是 161 条独立规则，而是 **5 种遍历方向 × 8 种查询目标 × 实体枚举 × 过滤条件组合** 的笛卡尔积子集；本体 link 结构决定哪些组合合法。

## 2. 过滤条件数量分布（161 模板）

| 条件数 | 模板数 | 占比 |
|---|---|---|
| 0 条 | 40 | 24.8% |
| 1 条 | 87 | 54.0% |
| 2 条 | 34 | 21.1% |

- 过滤算子 7 种：为 / 包含 / 不包含 / 以…开头 / 以…为后缀 / 不低于 / 大于、少于、低于
- 多条件仅 AND（"且/，/且"），不支持 OR 组合（OR 仅出现在"站点下有 A或B或C告警"类模板）

## 3. 遍历深度分布

| 嵌套深度 | 模板数 | 说明 |
|---|---|---|
| 0 步 | 77 | 直接查实体 |
| 1 步 | 65 | 所在的/产生的/的{子部件}/在{时间}/下连 |
| 2 步 | 16 | 站点/租户→设备→子部件；子部件→设备→指标 |
| 3 步 | 3 | 租户→站点→设备→子部件 KPI（最深） |

**遍历方向 5 种**：无、所在的、产生的、的{子部件}、在{时间}、下连。
**合法性约束**（query-gen.md）：
- `产生的` 仅当实体有 data_link→EventSet
- `的{子部件}` 仅当实体有 contains 关系
- `在{时间}{kpi}` 仅当实体有 data_link→MetricSet
- `下连` 仅当实体有 entity_set_link→physical_link

## 7. 组合合法性矩阵（遍历方向 × 实体能力）

| 遍历方向 | 需要的能力 | 网络 | PON | 服务器 | 存储 | 终端 | 协作 | 站点 | 租户 | 子部件 |
|---|---|---|---|---|---|---|---|---|---|---|
| 无遍历 | — | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 所在的(站点/租户) | located_at/belongs_to | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — | — | ✓(部分) |
| 产生的(告警) | data_link→event | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — |
| 的{子部件} | contains | ✓ | ✗ | ✓ | ✓ | — | — | — | — | ✗ |
| 在{时间}{kpi} | data_link→metric | ✓ | ✓ | ✓ | ✓ | ✗ | ✗ | — | — | 部分 |
| 下连(链路) | connected_to_a/z | ✓ | ✓ | ✓ | ✓ | ✗ | ✗ | — | — | — |

> 终端/协作无 KPI、无子部件、无链路，查询面最窄；网络域查询能力最全。

## 8. 稀疏区与盲点（可扩展方向）

1. **告警时间维度**：模板中"时间算子 + 告警发生时间"组合少（仅 ALARMTIME 排序），可加"近7天发生的告警"。
2. **KPI 阈值条件**：`{kpi}不低于{值}` 的过滤组合在用例集中出现但模板占比低（§6.3/6.4）。
3. **子部件级指标**：`板卡CPU使用率`、`端口流量` 等部件级 KPI 已覆盖，但硬盘温度/IOPS 的 TOP N 未覆盖。
4. **多跳 + 指标**：深度 3 的"租户→站点→设备→子部件→KPI"类模板少（3 条），可扩展。
5. **跨表告警反向**："有告警的设备在{时间}的{kpi}"（§3.2）是告警→指标的正向嵌套，反向"由指标反查设备告警"未覆盖。
